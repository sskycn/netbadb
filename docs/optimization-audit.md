Heap ownership is a nonblocking advisory `flock` on the durable Heap data-file inode, held by the shared buffer state through its `PageManager`. The inode follows a staged-file rename, unlike a WAL generation, and does not conflict with Core's structured `<heap>.owner` identity file. The guard survives a dropped `HeapStorage` while a transaction still owns the buffer. A successful clean `close` synchronizes the files, verifies that no transaction is active, and unlocks the inode even if a completed transaction object remains in scope. The path's parent is canonicalized and subsequent I/O uses that path; file symlinks and hard links are rejected. The guard is acquired before WAL or recovery writes. A rejected open performs no file mutation. `inspect_recovery` uses read-only page and WAL handles without claiming mutation authority; Core inspects an already-open source Heap during replacement. It does not truncate incomplete WAL tails or remove WAL generations. A later recovery-style open independently acquires the inode lock before any mutation.

LSM direct-engine ownership is a nonblocking advisory `flock` on the LSM root directory inode. `create` acquires it before creating Manifest or WAL; `open_with_prepared_resolutions` acquires it before reading Manifest or WAL, orphan cleanup, or prepared-transaction resolution. The shared transaction state retains the directory descriptor if the storage object is dropped. A clean `close` verifies quiescence, flushes and syncs, then unlocks, including when a completed transaction handle remains. A rejected open cannot mutate the files, and `inspect_recovery` remains read-only while another process owns the engine. Canonical directory aliases share the same inode. No disk or wire format or sidecar layout changed.

The A2 Heap transfer is explicit. `PageManager` opens and locks the data inode; `BufferPool` and transaction handles may extend that open file description. Ordinary clean `close` flushes, checks quiescence, and explicitly unlocks; `stop_for_promotion` instead flushes and stops the writer, duplicates the locked descriptor, and returns a non-cloneable `HeapOwnership`. The old object cannot write after this transfer. Core moves owner/WAL/status/alternate names while the source data name and lock remain, then moves data last with an atomic no-replace rename. The token checks the final pathname against the same open inode before it is consumed by `open_with_ownership`, which derives WAL/status/change-stream paths from the final name. The duplicate descriptor is closed by Drop and never calls `LOCK_UN`, so dropping the stopped object cannot release the handoff lock. If the transfer fails, no live writer remains; the token (if still in scope) retains ownership until it drops, after which normal recovery can retry. A private staged Heap cannot enable a change stream through Core; unexpected stream sidecars at either name fail promotion closed, and direct token rebinding also rejects path-bound stream sidecars.

For coordinator recovery, Core acquires all Heap data locks in path order before inspecting prepared transactions. Recovery decisions use that inspection while the locks remain held; each token is consumed by the actual Heap open. Catalog path override discovery and `validate_physical` are read-only observations. `recover_physical_with_ownership` rechecks every Heap descriptor under the acquired inode locks before any participant recovery. Startup mutation replay retains Heap tokens across its internal open/close passes and hands them to the final registry open. A direct read-only inspection is diagnostic only and does not claim a consistent snapshot against an active writer.

## A4.1 public WAL and Heap ownership

The confirmed public bypass was `netbadb_heap::WalManager::{create,open,append,close}` (also re-exported by `netbadb_storage`). `open` opens selected WAL generations writable, may truncate an incomplete tail, synchronizes the selected generation and parent directory, and removes superseded generations. `create` creates and synchronizes a generation. A live manager can append, flush and checkpoint through the public surface. Before A4.1, neither public WAL writer admission nor `PageManager::open` participated in Heap's data-inode lock. Both paths were callable by an external crate; a page manager returned writable page operations.

The working-tree implementation gives every logical WAL root a stable adjacent `<wal-root>.owner-lock` file. Public standalone WAL create/open and Heap's internal create/recovery use the same nonblocking exclusive lock. The lock is acquired before WAL generation inspection or repair and stays with the manager through append, sync, rotation, close, and Drop. Rotation retains the owner while generation files are replaced. Heap admission acquires the data inode first and then every exact WAL carrier selected by the durable recovery plan in carrier-path order; `HeapOwnership` retains them across inspection and promotion, then transfers the final-root token into recovery/open. Before Core promotes a staged WAL companion, it creates a hard-link alias for the owner carrier at the final WAL root when that path is unused. This keeps one locked inode reachable through the WAL rename window. If the final root already has a distinct stable carrier, recovery locks both carriers and keeps the final carrier. Failed promotion retains both. After ownership has rebound and promotion succeeds, `HeapOwnership::rebind` retires only the now-obsolete staging carrier or redundant hard-link alias while the final carrier remains locked, then syncs the parent directory. The public Heap resource manifest and Core retired-Heap GC manifest include the carrier. Loser cleanup leaves it in place; if it is the only remaining entry, the transaction staging directory remains as its stable pathname. Mixed recovery inventories admit only canonical carrier filenames derived from that transaction's staging locator. Retired-Heap GC records the carrier but does not unlink it, including across completed-GC reopen; `total_present_bytes` and deletion reports count only reclaimed bytes. The final owner carrier remains outside cleanup. The owner file is an intentional file-layout/open-behavior addition; it does not change WAL bytes or page encoding. Old binaries do not honor it and are not safe concurrent peers.

`PageManager::open` is also a writable API, so it now takes the existing nonblocking data-inode lock. This makes it mutually exclusive with Heap ownership while preserving standalone page-file use. `PageManager::inspect_read_only` and WAL recovery inspection remain read-only paths; WAL inspection does not create/claim an owner file, repair tails, rotate, or delete generations. It is diagnostic observation and does not promise a stable snapshot concurrent with an active writer.

The new external integration test exercises only crate exports. It starts a child process while Heap owns the data and WAL, checkpoints to rotate the WAL generation, then proves raw WAL and page opens are rejected and the file contents and directory listing remain unchanged. The reverse test holds a public WAL writer and proves Heap open rejects before recovery changes files, then succeeds after the WAL writer closes. A standalone writer contention/close/reopen case also passes. The child has a bounded timeout. This is direct public-entry evidence; the child path is not supplied with test-only access.
